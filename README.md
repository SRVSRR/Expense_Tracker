# Expense Tracker API

A privacy-focused personal finance API for manually entered income and expense tracking. The service provides authenticated account and transaction management, recurring transaction projections, budgeting analysis, forecasting, anomaly detection, and rule-based/ML-assisted categorization.

This repository currently contains the **FastAPI backend only**. Mobile and desktop clients are separate consumers of this API.

## Architecture

```text
Client applications
        |
        | HTTPS + JSON + Bearer JWT
        v
FastAPI application (backend/main.py)
        |
        +-- Auth and user isolation
        +-- CRUD routes
        +-- Forecast and budget services
        +-- Categorization rules and LightGBM model
        +-- Alembic migrations
        v
SQLAlchemy async database layer
        |
        +-- SQLite for local development
        +-- PostgreSQL/Supabase for hosted environments
```

The API uses asynchronous SQLAlchemy sessions and `aiosqlite` locally. PostgreSQL is supported through `asyncpg`. Application startup runs Alembic migrations before serving requests.

## Capabilities

### Implemented

- User registration, login, and current-user lookup
- Local JWT bearer authentication with bcrypt password hashes
- User-scoped account CRUD
- User-scoped income and expense transaction CRUD
- Account balance updates when transactions are created, amount-edited, or deleted
- User-scoped category CRUD
- Manual recurring rules and upcoming occurrence expansion
- Rolling 90-day cash-flow forecast
- Runway calculation based on average net daily burn
- Category anomaly detection using a 2x category-average rule
- Rule-based budget recommendations and category spending analysis
- Keyword categorization with LightGBM/TF-IDF fallback and correction logging
- Prediction caching with per-type TTLs
- OpenAPI, Swagger UI, and ReDoc generated by FastAPI

### Planned

- Scheduled prediction generation
- Confidence ranges for forecast results
- Automatic recurring-transaction detection
- Broader integration-test coverage and CI
- Production CORS hardening and operational monitoring

## Requirements

- macOS, Linux, or Windows
- Python 3.13 recommended
- Git
- A Supabase PostgreSQL database using the Transaction pooler
- A hosting account for deployment, such as Railway or Render

The ML categorizer additionally uses LightGBM, scikit-learn, NumPy, and pandas. These are listed in [backend/requirements.txt](backend/requirements.txt).

## Quick start

From the repository root:

```sh
cd backend
python3.13 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
uvicorn main:app --reload
```

On Windows PowerShell, activate the environment with `venv\\Scripts\\Activate.ps1` and use `py -3.13` in place of `python3.13`.

The local server is available at:

- API root: http://127.0.0.1:8000/
- Health check: http://127.0.0.1:8000/health
- Swagger UI: http://127.0.0.1:8000/docs
- ReDoc: http://127.0.0.1:8000/redoc
- OpenAPI JSON: http://127.0.0.1:8000/openapi.json

The first startup runs migrations against the configured Supabase database. Stop the development server with `Ctrl+C`.

## Configuration

Copy [backend/.env.example](backend/.env.example) to `backend/.env`. Do not commit the resulting `.env` file.

```env
DATABASE_URL=postgresql+asyncpg://postgres.<project-ref>:<password>@<pooler-host>:6543/postgres
SECRET_KEY=replace-with-a-long-random-value
SUPABASE_JWKS_URL=https://<project-ref>.supabase.co/auth/v1/.well-known/jwks.json
SUPABASE_ISSUER=https://<project-ref>.supabase.co/auth/v1
TESTING=0
ACCESS_TOKEN_EXPIRE_MINUTES=1440
```

### Environment variables

| Variable | Required | Description |
|---|---:|---|
| `DATABASE_URL` | Yes in production | Async SQLAlchemy URL. Use `sqlite+aiosqlite:///./expense_tracker.db` locally or `postgresql+asyncpg://...` for PostgreSQL. |
| `SECRET_KEY` | Yes in tests | Local HS256 test-token secret; Supabase signs production tokens. |
| `SUPABASE_JWKS_URL` | Yes in production | Supabase JWKS endpoint used to verify RS256 access tokens. |
| `SUPABASE_ISSUER` | Yes in production | Supabase JWT issuer, normally `https://<project-ref>.supabase.co/auth/v1`. |
| `TESTING` | No | Set to `1` only for isolated tests; any other value uses Supabase JWT verification. |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | No | Local test-token lifetime. Defaults to 1440 minutes. |

`DATABASE_URL` is required; the application has no local SQLite fallback. For Supabase Transaction pooler connections, use port `6543` and the `postgresql+asyncpg://` driver form.

## Database and migrations

Migration files live in [backend/alembic/versions](backend/alembic/versions). The current schema includes:

- `accounts`
- `transactions`
- `categories`
- `recurring_rules`
- `predictions`
- `correction_logs`

Run migrations manually from `backend` when preparing a release or a new database:

```sh
cd backend
source venv/bin/activate
alembic upgrade head
```

Useful commands:

```sh
alembic current
alembic history
alembic downgrade -1
```

Do not use `alembic downgrade` in production without a tested rollback plan. Back up PostgreSQL before schema changes. The startup lifespan also runs `alembic upgrade head`, so the deployment identity must have permission to run migrations, or migrations should be run as a separate release step.

## Authentication

Production authentication is handled by Supabase Auth. Create a session in the
client with `@supabase/supabase-js` using email/password, magic link, or OAuth,
then send the returned access token as a bearer token.

For a protected request:

```sh
curl https://expense-tracker-uwrp.onrender.com/api/auth/me \
  -H 'Authorization: Bearer YOUR_ACCESS_TOKEN'
```

All business endpoints require a valid bearer token. The token subject identifies the user, and route queries must be scoped to that user. Clients should store the token in platform-secure storage and clear it when a request returns HTTP 401.

## API reference

All paths below are relative to the deployed API base URL. A trailing slash is accepted by the route definitions shown here.

### Health and metadata

| Method | Path | Auth | Purpose |
|---|---|---:|---|
| GET | `/` | No | API identity and documentation links |
| GET | `/health` | No | Liveness check |
| GET | `/docs` | No | Swagger UI |
| GET | `/openapi.json` | No | Machine-readable API schema |

### Authentication

| Method | Path | Auth | Purpose |
|---|---|---:|---|
| GET | `/api/auth/me` | Yes | Return the authenticated user |

### Accounts

| Method | Path | Auth | Purpose |
|---|---|---:|---|
| GET | `/api/accounts/` | Yes | List the user's accounts |
| POST | `/api/accounts/` | Yes | Create an account |
| GET | `/api/accounts/{account_id}` | Yes | Read one account |
| PUT | `/api/accounts/{account_id}` | Yes | Update account fields |
| DELETE | `/api/accounts/{account_id}` | Yes | Delete an account |

Account creation sets `current_balance` to `initial_balance`. Transaction creation then changes the current balance according to transaction type.

### Transactions

| Method | Path | Auth | Purpose |
|---|---|---:|---|
| GET | `/api/transactions/` | Yes | List transactions with filters and pagination |
| POST | `/api/transactions/` | Yes | Create an income or expense |
| GET | `/api/transactions/{transaction_id}` | Yes | Read one transaction |
| PUT | `/api/transactions/{transaction_id}` | Yes | Update transaction fields |
| DELETE | `/api/transactions/{transaction_id}` | Yes | Delete a transaction and reverse its balance effect |

Supported list query parameters include `account_id`, `type`, `category`, `start_date`, `end_date`, `limit`, and `offset`.

Example account and transaction flow:

```sh
ACCOUNT_ID=$(curl -s -X POST http://127.0.0.1:8000/api/accounts/ \
  -H 'Authorization: Bearer YOUR_ACCESS_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"name":"Checking","currency":"USD","initial_balance":1000}' \
  | python -c 'import json,sys; print(json.load(sys.stdin)["id"])')

curl -X POST http://127.0.0.1:8000/api/transactions/ \
  -H 'Authorization: Bearer YOUR_ACCESS_TOKEN' \
  -H 'Content-Type: application/json' \
  -d "{\"account_id\":\"$ACCOUNT_ID\",\"type\":\"expense\",\"amount\":42.50,\"category\":\"Food\",\"description\":\"Lunch\",\"date\":\"2026-09-04T12:00:00\"}"
```

### Categories

| Method | Path | Auth | Purpose |
|---|---|---:|---|
| GET | `/api/categories/` | Yes | List categories |
| POST | `/api/categories/` | Yes | Create a category |
| GET | `/api/categories/{category_id}` | Yes | Read one category |
| PUT | `/api/categories/{category_id}` | Yes | Update a category |
| DELETE | `/api/categories/{category_id}` | Yes | Delete a category |

### Recurring transactions

| Method | Path | Auth | Purpose |
|---|---|---:|---|
| GET | `/api/recurring/` | Yes | List recurring rules |
| POST | `/api/recurring/` | Yes | Create a recurring rule |
| GET | `/api/recurring/upcoming` | Yes | Expand upcoming occurrences |
| DELETE | `/api/recurring/{rule_id}` | Yes | Delete a recurring rule |

A recurring rule accepts `pattern`, `frequency`, `expected_amount`, `expected_date`, and an optional `transaction_id`. Current expansion supports `daily`, `weekly`, `monthly`, and `yearly` patterns. Automatic creation of a rule from `is_recurring` is planned and is not yet complete.

### Forecasting and budgets

| Method | Path | Auth | Purpose |
|---|---|---:|---|
| GET | `/api/forecast/cashflow?days=30` | Yes | Project balances for 7-365 days |
| GET | `/api/forecast/runway?threshold=0` | Yes | Estimate days until a balance threshold |
| GET | `/api/forecast/anomalies` | Yes | Find expense outliers |
| GET | `/api/budget/recommendations` | Yes | Return category budget recommendations |
| GET | `/api/budget/category-analysis` | Yes | Return spending totals by category |

Forecast and budget results are cached in the `predictions` table. Current cache lifetimes are 24 hours for cash flow and anomalies, 12 hours for runway, and 7 days for budget outputs. Transaction and account mutations invalidate derived predictions.

### Categorization

| Method | Path | Auth | Purpose |
|---|---|---:|---|
| POST | `/api/categorize/suggest` | Yes | Suggest a category using ML/rules |
| POST | `/api/categorize/corrections` | Yes | Store a user correction |
| POST | `/api/categorize/train` | Yes | Train the shared categorizer from corrections |
| GET | `/api/categorize/model-info` | Yes | Inspect model state |

The categorizer uses a rule-based fallback when no model exists or confidence is below the configured threshold. Training requires at least 30 correction samples. Training currently uses correction records from all users, which is intentional for a shared model but should be reviewed before production.

## Integration guide

### HTTP contract

- Send JSON request bodies with `Content-Type: application/json`.
- Send `Authorization: Bearer <token>` on all protected requests.
- Treat `401` as an expired or invalid session and require login again.
- Treat `404` as either a missing resource or a resource belonging to another user.
- Treat `422` as request validation failure and display or log the returned field errors.
- Use the OpenAPI document at `/openapi.json` to generate typed clients where practical.

### Client base URL

Use one configurable base URL per environment:

```text
Development: http://127.0.0.1:8000
Production:  https://expense-tracker-uwrp.onrender.com
```

Mobile devices cannot reach a computer's `127.0.0.1`; use the development machine's LAN address or a secure tunnel during local device testing. Never ship a database URL or `SECRET_KEY` in a client application.

### Example TypeScript request helper

```ts
const API_BASE_URL = process.env.EXPENSE_API_URL;

async function apiRequest<T>(path: string, token?: string, init: RequestInit = {}): Promise<T> {
  const response = await fetch(`${API_BASE_URL}${path}`, {
    ...init,
    headers: {
      "Content-Type": "application/json",
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
      ...init.headers,
    },
  });

  if (!response.ok) {
    const body = await response.text();
    throw new Error(`API ${response.status}: ${body}`);
  }

  return response.status === 204 ? (undefined as T) : response.json();
}
```

The client should keep authentication state separate from cached financial data, retry only idempotent requests, and avoid logging passwords, bearer tokens, or sensitive transaction descriptions.

### Integrating another backend

A server-to-server integration should:

1. Register or provision a user through the auth contract.
2. Store the returned JWT only in a server-side secret store.
3. Call the API over HTTPS.
4. Map the external system's account IDs to the API's account IDs.
5. Use idempotency or an external transaction reference at the integration boundary. The current API does not yet expose an idempotency key, so callers must prevent duplicate retries themselves.
6. Respect user ownership and never reuse one user's token for another user.

## Deployment

The backend is deployed on Render at `https://expense-tracker-uwrp.onrender.com`.
A Render deployment uses:

- Build command: `pip install -r backend/requirements.txt`
- Start command: `cd backend && uvicorn main:app --host 0.0.0.0 --port $PORT`
- Health check path: `/health`
- Required secrets: `DATABASE_URL`, `SUPABASE_JWKS_URL`, `SUPABASE_ISSUER`
- Recommended setting: `TESTING=0`

### PostgreSQL/Supabase setup

1. Create a Supabase project.
2. Copy a pooled PostgreSQL connection string.
3. Convert the driver to the async SQLAlchemy form, such as `postgresql+asyncpg://...`.
4. Set `DATABASE_URL` in the hosting provider.
5. Set `SUPABASE_JWKS_URL` and `SUPABASE_ISSUER` for the Supabase project.
6. Run `alembic upgrade head` from `backend`, either as a release command or during startup.
7. Verify `/health` and one protected CRUD request using a Supabase access token.

Supabase provides both the production database and authentication provider. The
backend verifies Supabase-issued RS256 tokens through the project's JWKS endpoint.

### Production CORS

The current code permits all origins for development convenience. Before exposing browser-based clients, replace the wildcard with an allowlist of known HTTPS origins. Native mobile clients do not use browser CORS in the same way, but the API should still use restrictive production defaults.

### Release verification

```sh
curl https://expense-tracker-uwrp.onrender.com/health
curl https://expense-tracker-uwrp.onrender.com/openapi.json
```

Then exercise registration, login, account creation, transaction creation, forecast retrieval, and a cross-user access test. Configure uptime monitoring, centralized logs, error tracking, database backups, and TLS before real users depend on the service.

For the full operational checklist, see [docs/INFRASTRUCTURE.md](docs/INFRASTRUCTURE.md).

## Operations and security

- Use HTTPS for all non-local traffic.
- Generate a high-entropy `SECRET_KEY` per environment.
- Keep `.env`, database URLs, JWTs, and model-training data out of source control and logs.
- Restrict database network access to the API and administrative paths.
- Enable PostgreSQL backups and test restoration.
- Add rate limiting to registration, login, and ML training before public launch.
- Configure CORS per environment.
- Run dependency and vulnerability scans in CI.
- Keep migrations reversible where practical and back up before destructive changes.
- Add database connectivity to the health/readiness checks before autoscaling.
- Review whether shared ML training data is acceptable for the product's privacy model.

## Current limitations

- The repository is API-only; no frontend is currently part of this project.
- Integration tests for the complete endpoint surface are still pending.
- Supabase Auth is required in production; local HS256 tokens are test-only.
- The documented automatic `is_recurring` to recurring-rule workflow is not complete.
- Changing a transaction's type or account is not yet supported as a balance-preserving operation; amount changes are handled.
- Forecasting uses LightGBM regressors with rolling, lag, velocity, and seasonality features.
- Prediction generation is request-driven; scheduled jobs are not yet implemented.
- CORS is permissive by default and must be hardened for production.
- The API does not yet provide idempotency keys for safe external retries.
